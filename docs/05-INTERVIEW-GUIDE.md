# 05 — Accelya DevOps interview guide

## 30-second project explanation

> I built a production-style airline booking platform to practice the complete DevOps lifecycle. The API is containerized with Docker, tested through GitHub Actions, scanned with Trivy, stored in ECR, and deployed to EKS using Helm. Terraform provisions the VPC, EKS, RDS PostgreSQL, ECR and IAM. I use AWS Secrets Manager with External Secrets for database credentials, ALB for ingress, Prometheus/Grafana for observability, Metrics Server and HPA for scaling, and GitHub OIDC so CI/CD does not need long-lived AWS keys. I also deliberately introduced failures such as CrashLoopBackOff, image pull failures, readiness failures and rollout regressions and used Kubernetes evidence plus RCA rather than guessing.

## High-value scenario answers

### “A deployment succeeded but users receive 503. What do you do?”

1. Confirm scope and timestamp.
2. Check ALB status and target health.
3. Check Ingress events.
4. Check Service and Endpoints.
5. Check pod readiness.
6. Check application logs.
7. Compare the deployed image SHA with the release.
8. If the release caused the issue and rollback is safe, rollback.
9. Validate with health/readiness and a real request.
10. Document the root cause and prevention.

### “A pod is CrashLoopBackOff.”

> I do not treat CrashLoopBackOff as the root cause. I check `describe` for events and `logs --previous` for the terminated process. Then I classify it as configuration, dependency, application startup, probe, resource or image-related before changing anything.

### “How do you troubleshoot high CPU?”

> First I establish whether the increase is real and whether it affects latency/error rate. I use `kubectl top`, Prometheus metrics and application request metrics. Then I check whether HPA is reacting, whether the workload has sensible CPU requests/limits, whether traffic changed, and whether a recent release correlates with the spike. I avoid increasing limits blindly because that can hide a performance problem.

### “How do you secure secrets?”

> I avoid putting database credentials in Git or Helm values. In this lab, credentials are generated by Terraform and stored in AWS Secrets Manager. External Secrets retrieves the required value into Kubernetes, and the workload consumes it as an environment variable. For a production team I would also protect Terraform state because sensitive values can appear in state depending on resource usage.

### “How does HPA work?”

> HPA reads metrics through the Metrics API, compares current utilization against the target, calculates the desired replica count and updates the workload's scale target. The Deployment then creates or removes pods. HPA is not the same thing as node scaling; if pods cannot be scheduled, node capacity becomes the next problem.

### “Why use Terraform and Helm together?”

> Terraform manages cloud infrastructure and its lifecycle—VPC, EKS, RDS, ECR and IAM. Helm manages Kubernetes application packaging and release lifecycle. I keep the boundaries clear rather than making Terraform own every Kubernetes object.

### “Why ECR instead of rebuilding in the cluster?”

> I want an immutable artifact. CI builds and scans one image, pushes it to ECR, and deployment references the exact Git SHA. That makes promotion, rollback and incident correlation much easier.

## Five STAR stories from the lab

### Story 1 — Production-style incident

**Situation:** API pods became unhealthy during a configuration change.

**Task:** Restore traffic without making the incident worse.

**Action:** Checked rollout status, pod events, previous logs and readiness. Identified the startup/configuration failure, corrected the Helm value and watched the rollout.

**Result:** Service returned to healthy state and the incident produced a runbook improvement.

### Story 2 — Security

**Situation:** Trivy reported a high-severity dependency/base-image vulnerability.

**Task:** Prevent a vulnerable image from being promoted.

**Action:** Identified the package, checked whether a fixed version existed, updated the dependency/base image, rebuilt, retested and rescanned.

**Result:** The image passed the security gate and the dependency became reproducible through version pinning.

### Story 3 — Reliability

**Situation:** A deployment could make the API unavailable if all old pods disappeared before new pods were healthy.

**Task:** Reduce deployment risk.

**Action:** Used rolling updates with `maxUnavailable: 0`, readiness probes and a PDB.

**Result:** Kubernetes keeps an available replica while replacing pods, and unhealthy pods are excluded from traffic.

### Story 4 — Cost

**Situation:** The lab needed AWS infrastructure without turning into an unnecessarily expensive environment.

**Task:** Keep the learning environment small.

**Action:** Used two small worker nodes, a single NAT gateway, a small RDS instance and short retention settings.

**Result:** The lab remains representative while avoiding unnecessary production-scale capacity.

### Story 5 — CI/CD credentials

**Situation:** A deployment pipeline needs AWS access.

**Task:** Avoid long-lived AWS access keys in GitHub.

**Action:** Configured GitHub OIDC trust for a dedicated IAM role and scoped the role to ECR push operations for the lab.

**Result:** The pipeline obtains short-lived credentials from AWS STS at runtime.

## Honest production-readiness answer

> This lab is production-style rather than production infrastructure. Before real production I would add a remote encrypted Terraform backend with locking, stronger IAM policy review, private EKS endpoint strategy where appropriate, multi-AZ RDS, automated backups and restore tests, centralized logs, alert routing, SLOs, network policies, image signing/SBOM, policy-as-code, environment separation, disaster recovery testing and a formal change-management process.

That answer shows you understand the difference between a working lab and a production platform.
